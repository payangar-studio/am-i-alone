Switching forms

A companion changes form on the server, in one tick, handing everything over; the client never sees it.

In game

Nothing shows. A companion changing form keeps walking, attacking or standing as it was, with everything it has: no flicker, no item lost, no item doubled.

How it is built

What triggers a switch

DecisionThe core decides. Its rule (anchor form in follow mode with an owner, anchored form otherwise) is evaluated again whenever what it reads changes: the mode, the owner. Until ownership is built, a test command switches a companion, and gives the anchor form the player who runs it as its owner, so that saving works as designed (Saving).

One living form, handed over whole

DecisionOne living form at any time, handed over whole in one server tick, in the world and at the place where the companion is. No copy stays elsewhere, so there is nothing to keep in sync.
StepAnchored to anchorAnchor to anchored
1. SaveVanilla's entity save (saveWithoutId): the same contents for both forms, since both are Players: inventory, equipment, ender chest, experience, abilities, health, food, effects, position, rotation, Brain memories, the coreThe same
2. RemoveDiscarded (RemovalReason.DISCARDED, which vanilla does not save): its chunk forgets itOut of the world's list of players (removePlayerImmediately)
3. CreateThe core restores the profile; the anchor form loads the save and takes the old entity id (setId)The same, for the anchored form
4. AddA fake connection, then level.addNewPlayeraddFreshEntity

The entity id is reused as vanilla does when a player respawns (PlayerList.respawn). The anchored form is discarded rather than unloaded so that its chunk cannot save it and bring it back next to the new form.

DecisionA test checks that a round trip between the forms keeps the inventory and the equipment exactly, with nothing lost or duplicated.

The client keeps its entity

DecisionThe client entity is the companion's facade; the forms change behind it, on the server only.
  1. The server first sends a mod packet to the clients that see the companion: "the companion of entity id N changes form". A client that has an entity N marks it; one that has none ignores the packet.
  2. The server saves the old form and removes it: vanilla sends the removal of N, which a client that marked N ignores.
  3. The server creates the new form with entity id N and adds it: vanilla sends its arrival, which the client ignores too. The ClientCompanion stays the same object, and the mark is cleared.
  4. The server sends the new form's data, as for any entity: the client applies it to the same object.
DecisionThe ignoring is done by a client mixin on handleRemoveEntities and handleAddEntity of ClientPacketListener, for marked entities only. No vanilla or Fabric API keeps an entity on the client across a removal.
FactRead in the 26.3 code: without it, the client removes its entity and builds a new one (ClientLevel.addEntity discards an entity with the same id first), and what the client and the animation mods keep on the entity starts over: a Better Combat attack would be cut.

Open questions

QuestionChecking it in game. A switch in the middle of a Better Combat attack, and while walking, must not show.
QuestionA companion riding, dead or dying. Dismount first, wait, or refuse.
QuestionA client that starts seeing the companion during the switch. Whether it can receive the arrival without the notice, to check against how vanilla tracks entities.

Ruled out

OptionWhy it is ruled out
A separate central inventoryOne living form handed over whole already rules out loss and duplication; a second copy would add the desync it was meant to prevent
Handing the client state over to a new client entityWhat the animation mods add to the entity is lost, unless every field is copied by reflection
Reviving the removed client entityVanilla never does it, and mods that clean up an entity's data on removal will have dropped it already
