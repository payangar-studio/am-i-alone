Shared identity

A companion is one identity, its core, carried by whichever form it has. The forms only hold what vanilla requires.

Why a core

DecisionThe two forms extend different vanilla classes (Player and ServerPlayer), so the logic cannot live in a shared parent class: Java has one parent per class. It lives in an object, the companion's core, that the current form carries.
  1. The core holds the companion's identity and state. It is saved in the form's data and moves from one form to the other with it.
  2. The forms only do what vanilla requires (their type, saving, the spawn packet, the tick) and hand the rest to the core through an interface both forms implement.
  3. The Brain lives inside the form, as in any vanilla creature, and its memories are saved with it. It accepts any living entity, so a behaviour such as "follow the owner" is written once for both forms.
  4. The motor turns the Brain's intentions into player inputs: vanilla's pathfinding requires a Mob, and neither form is one.

One identity, defined once

DecisionThe identity (UUID, name, skin) is one piece of data, defined once in the core, carried by the current form and synced to the clients as a Fabric synced attachment. Not a synced entity data declared in both forms and in the client class, where any offset between the three breaks the sync.
  1. The identity is defined once, in the core.
  2. Whichever form the companion has carries it, as a Fabric synced attachment of the entity.
  3. Fabric sends it to every client that sees the entity; the facade takes its name and skin from it.
FactRead in the 26.3 code: Player takes its UUID back from its profile on every load (readAdditionalSaveData). A form rebuilt from saved data would change identity: the core restores the profile (UUID, name, skin) before the form uses it.

The companion type

FactPlayer sets its type to minecraft:player in its constructor. Both forms override getType() and typeHolder() to carry am_i_alone:companion, which is what saving and the network read. A private field of Entity still holds minecraft:player, and a few methods read it directly (default name, loot table, size, network update interval). These values are a player's today, so they match; a test covers this coupling.
